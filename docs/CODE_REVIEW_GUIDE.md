# 代码审查指南

## 目的

代码审查是确保代码质量、知识共享和团队协作的重要环节。本指南旨在帮助审查者和被审查者更好地进行代码审查。

## 审查者指南

### 审查重点

#### 1. 代码质量

- **可读性**: 代码是否清晰易懂？
- **命名**: 变量、函数、类的命名是否有意义？
- **注释**: 复杂逻辑是否有适当的注释？
- **格式**: 代码格式是否符合项目规范？

#### 2. 设计与架构

- **设计模式**: 是否使用了合适的设计模式？
- **SOLID 原则**: 是否遵循 SOLID 原则？
- **依赖关系**: 模块间的依赖是否合理？
- **可扩展性**: 代码是否易于扩展？

#### 3. 功能正确性

- **需求实现**: 是否完整实现了需求？
- **边界情况**: 是否处理了边界情况？
- **错误处理**: 错误处理是否完善？
- **测试覆盖**: 是否有足够的测试？

#### 4. 性能

- **算法复杂度**: 时间和空间复杂度是否合理？
- **资源使用**: 内存、CPU 使用是否优化？
- **异步处理**: 是否正确使用异步操作？
- **缓存策略**: 是否有合理的缓存？

#### 5. 安全性

- **输入验证**: 是否验证了用户输入？
- **权限检查**: 是否有适当的权限控制？
- **敏感数据**: 敏感数据是否安全处理？
- **依赖安全**: 第三方依赖是否安全？

#### 6. 用户体验

- **响应速度**: 操作是否流畅？
- **错误提示**: 错误信息是否友好？
- **加载状态**: 是否有适当的加载提示？
- **无障碍**: 是否考虑了无障碍访问？

### 审查流程

1. **理解上下文**
   - 阅读 PR 描述和相关 Issue
   - 了解变更的目的和背景

2. **整体浏览**
   - 快速浏览所有变更
   - 理解整体架构和设计

3. **详细审查**
   - 逐行审查代码
   - 关注上述审查重点

4. **测试验证**
   - 检出分支本地测试
   - 验证功能是否正常

5. **提供反馈**
   - 使用建设性的语言
   - 提供具体的改进建议
   - 区分必须修改和建议优化

### 反馈示例

#### ✅ 好的反馈

```
建议: 这个函数有点长（50+ 行），可以考虑拆分为几个小函数，提高可读性。

例如：
- extractUserData()
- validateUserData()
- saveUserData()
```

#### ❌ 不好的反馈

```
这段代码写得不好，需要重写。
```

### 反馈分类

使用标签区分反馈的重要性：

- **[必须]**: 必须修改的问题（bug、安全问题）
- **[建议]**: 建议优化的地方（性能、可读性）
- **[疑问]**: 需要讨论的问题
- **[赞]**: 值得学习的好代码

## 被审查者指南

### 提交前检查

- [ ] 代码已通过 `flutter analyze`
- [ ] 代码已通过 `dart format`
- [ ] 所有测试通过
- [ ] 更新了相关文档
- [ ] 更新了 CHANGELOG.md
- [ ] PR 描述清晰完整

### 响应反馈

1. **及时响应**
   - 尽快回复审查意见
   - 说明修改计划或不同意见

2. **虚心接受**
   - 以学习的心态对待反馈
   - 不要防御性回应

3. **讨论分歧**
   - 如有不同意见，礼貌讨论
   - 提供技术依据

4. **标记完成**
   - 修改后标记为已解决
   - 说明修改内容

### 自我审查清单

在提交 PR 前，先进行自我审查：

#### 代码质量
- [ ] 代码清晰易读
- [ ] 命名有意义
- [ ] 没有重复代码
- [ ] 注释适当

#### 功能
- [ ] 功能完整
- [ ] 边界情况处理
- [ ] 错误处理完善
- [ ] 用户体验良好

#### 测试
- [ ] 单元测试覆盖
- [ ] 集成测试通过
- [ ] 手动测试验证

#### 性能
- [ ] 没有性能问题
- [ ] 资源使用合理
- [ ] 动画流畅

#### 兼容性
- [ ] 多平台测试
- [ ] 不同屏幕尺寸
- [ ] 向后兼容

## 代码审查最佳实践

### 1. 小而频繁

- 保持 PR 小而专注
- 一次只做一件事
- 频繁提交，快速迭代

### 2. 清晰沟通

- PR 描述详细
- 提供上下文信息
- 说明设计决策

### 3. 自动化

- 使用 CI/CD 自动检查
- 自动化测试
- 自动化格式检查

### 4. 建设性反馈

- 使用"我们"而不是"你"
- 提问而不是命令
- 提供具体建议

### 5. 及时响应

- 24 小时内响应
- 优先级高的 PR 优先审查
- 避免阻塞开发

## 常见问题

### Q: 审查需要多长时间？

A: 取决于 PR 大小，通常：
- 小 PR（< 100 行）: 15-30 分钟
- 中 PR（100-500 行）: 30-60 分钟
- 大 PR（> 500 行）: 1-2 小时

### Q: 如何处理意见分歧？

A: 
1. 礼貌讨论技术观点
2. 提供数据和依据
3. 必要时寻求第三方意见
4. 以项目利益为重

### Q: 什么时候可以批准 PR？

A: 当满足以下条件：
- 所有必须修改的问题已解决
- CI/CD 检查通过
- 功能正确实现
- 代码质量达标
